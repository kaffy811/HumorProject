# Post Dislike reaction — 2026-10-23

Posts now support Dislike beside Like in Feed, profile collections, recommendations, ranking cards/rows and detail controls. The button starts as an outlined broken heart; selecting it briefly shows the existing baby cry WebP, fading to a gray broken heart. Reduced-motion users see the final state immediately. Preview cards remain free of actions.

Like and Dislike are mutually exclusive. Both can be toggled off. Shared controls optimistically patch the existing SWR caches, including detail, collections, profile totals and rankings; a failed request restores both flags and the Like count and displays the global Toast. Duplicate controls serialize in-flight reactions for the same post. Dislikes do not subtract from other users' Likes or change ranking rules.

## Database and access

Migration: `202610230001_post_dislike.sql`. The existing vote value `-1` stores Dislike; the unique member/post constraint guarantees exclusion atomically. A service-only reaction RPC uses advisory transaction locks and the existing private request ledger for retry idempotency. The original Like RPC delegates to it for backwards compatibility. Feed and post DTOs expose only the current viewer's `viewerHasDisliked` flag. Dislikes generate no notification; switching away from Like removes the existing unread Like notification through the existing trigger. Auth, Google checks, RLS and author deletion rules are unchanged.

Before production migration, the application schema/data/functions/grants/RLS were backed up locally (ignored `deliverables/backups/2026-10-23-before-dislike.sql`, SHA-256 `1a54909724673f54453416544acb56c582c4ae38840b336d5347b8c5a5eee76c`). The backup covers public application tables, not Auth users or Storage object bytes. The migration was rehearsed in local in-memory PostgreSQL against that fresh backup before application.
